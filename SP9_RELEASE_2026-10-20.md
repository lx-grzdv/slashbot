## Корневые проблемы дня

### 1. Редактор падал на лимите Telegram вместо доставки

`prepare_editorial_digest()` перебирал лимиты выдержек 240→95 и при длине
выше `MAX_TELEGRAM_TEXT` (3900) бросал:

`Содержательные итоги не помещаются в один пост; события сохранены, выпуск требует сокращения`

При этом `split_digest()` и `delivery_batch` уже умеют многочастную доставку,
но до них выполнение не доходил. На данных утра минимальная длина была ~4035
(с погодой) — переполнение около 135 единиц UTF-16.

**Что изменено в коде (локально, не отдельный релизный коммит):**

- группировка простых строк `Completed (дата)` в одну строку на фразу;
- дополнительные лимиты выдержек 70 и 50;
- если после сжатия текст всё ещё длинный — вернуть самый короткий валидный
  вариант, а не падать; `split_digest` отправит частями;
- если текст ≤3900 — не дробить его из‑за запаса 80 под заголовок части.

### 2. Неполное чтение Updates у 24 карточек

Утренний выпуск: содержимое часто читалось, история/комментарии — нет.
Типичная ошибка: `Updates: Не удалось открыть Updates: edited: Locator.click:
Timeout 5000ms exceeded`. У «Вебинары с Рюдигером» дополнительно был
`navigation: Locator.wait_for` 45 с.

Список 24 целей: `.sp9_data/recovery-2026-10-20-cards/targets.json`.

Отдельный проход после доставки прочитал **24/24** (Guide — со второго захода).
Это снова ручной recovery, не автоматическое дополнение поста (задача C бэклога).

### 3. Автозапуск не закрыл день сам

После двух ошибок длины процесс ушёл в третью попытку полного перечитывания
и к обеду всё ещё работал без отправки. Резервные слоты 11:10 / 11:30 не
заменили застрявший job: один долгий процесс держал блокировку/`running`.

## Как не нарываться снова

Пока бэклог A–C не закрыт, день закрывает короткий контроль, а не ожидание ETA.

### Уже снижает риск (после правок 20.10)

- Текст чуть длиннее лимита не должен валить весь выпуск: группировка простых
  `Completed`, более жёсткие выдержки, возврат лучшего текста для `split_digest`.
- Очередь `pending_events` при отказе редактора сохраняется — события не теряются.
- Это работает только там, где крутится обновлённый `sp9_digest.py`. Без коммита
  и теста на другой копии репозитория баг «~4035 → raise» может вернуться.

### Риски, которые код ещё не закрывает

| Риск | Как не попасть |
| --- | --- |
| Updates не открылись у N карточек | Warning в посте = день не закрыт, пока не дочитали или явно не приняли неполный выпуск |
| Job висит часами | Не слушать ETA. Раз в 15–20 мин: `state=running` и есть ли прогресс в stdout / новый `last_attempt`. Тишина >10 мин после паузы 120 с или две ошибки «не помещается» подряд — смотреть stderr; при залипании остановить процесс и чинить/досылать |
| `--skip-if-sent-today` после неполного поста | Неполный + warning ≠ полный день. Авто-recovery поста нет (бэклог C) — дочитывание только вручную |
| Сырой текст (хуки SMM, `View 14 more`, имена zip) | Бэклог A: само не «вылечится». Либо править пост, либо терпеть до правок редактора |
| Фикс лимита не в git / без теста | Закрепить коммитом и регрессией «длина >3900 → не raise / уходит в split» |

### Чеклист буднего дня (~2 минуты, к ~12:00)

1. Пост за сегодня в чате есть?
2. Внизу нет `Не полностью прочитано карточек`? Если есть — recovery, как 19–20.10.
3. В состоянии: `last_successful_digest_date` = сегодня, `pending_events` пуст,
   `consecutive_failures` = 0, `last_error` пуст.
4. Если LaunchAgent `running` после 12:30 без прогресса в stdout — разбирать,
   не ждать «ещё 10 минут».

```bash

tail -n 20 .sp9_data/launchd.stdout.log

```

### Что закрыть в коде, чтобы не жить на чеклисте

По приоритету из [бэклога](SP9_STATUS_AND_BACKLOG.md):

1. **C** — после доставки с warning сам дочитать пропуски и `edit` тот же message id.
2. Коммит + тест на лимит Telegram / `prepare_editorial_digest` + `split_digest`.
3. **B** — дедлайн окна восстановления: один зависший pid не должен съедать день.
4. **A** — резать UI-шум и длинные цитаты в резюме.

Итог на 20.10: повтор «текст ~4035 → часы тишины без поста» обновлённый редактор
должен избегать; повтор «много карточек без Updates и простыня warning» —
пока только чеклистом и ручным recovery, пока нет автодополнения поста.
